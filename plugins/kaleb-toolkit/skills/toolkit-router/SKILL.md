# Toolkit Router

Choose one primary workflow before adding supporting tools.

1. Identify the task's main outcome.
2. Check which relevant skills and CLIs are available.
3. Select the smallest tool that can own the main outcome.
4. Add another tool only for a distinct supporting job.
5. Never claim that an external tool is installed when it is not available.

## Defaults

| Outcome | Start with | Use an alternative when |
|---|---|---|
| Engineering | [Matt Pocock Skills](https://github.com/mattpocock/skills) | Use [Superpowers](https://github.com/obra/superpowers) when the user wants a more prescriptive workflow. |
| Frontend design | [Impeccable](https://github.com/pbakaus/impeccable) | Use [Grill Design](https://github.com/will-ness-ai/skills/tree/main/skills/grill-design) to explore taste through repeated variants. |
| Web animation | [Oil Motion](https://github.com/oil-oil/oil-motion) | Use general frontend tools when motion is not the main outcome. |
| Natural writing | [Humanizer](https://github.com/blader/humanizer) | Edit directly when the change is small and specific. |
| CLI creation | [CLI Printing Press](https://github.com/mvanhorn/cli-printing-press) | Use normal engineering workflows when no generated CLI is needed. |
| Tasks | [Todoist CLI](https://github.com/Doist/todoist-cli) | Keep work in the current conversation when no durable task is needed. |
| Notes | [Obsidian Skills](https://github.com/kepano/obsidian-skills) | Keep work in the repository when it belongs with the code. |

External tools remain independent dependencies. Refer to their source
repositories for installation and current behavior.
